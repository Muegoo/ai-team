# Workflow CLI

`scripts/workflow.py` is a local planning and evidence reader. Orca remains the dispatch and lifecycle authority. The CLI never starts workers, acknowledges deliveries, settles tasks, makes architecture decisions, or merges changes.

For traceable spec-to-ticket planning, skill inventory, comparative pilot validation, project lessons, and fixed local checks, see [practices.md](practices.md). `scripts/contracts.py plan-input CONTRACT --root .` emits the `tasks` input accepted below; it does not execute acceptance verification descriptions.

## Plan

Run `python3 scripts/workflow.py plan PATH [--workers N] [--completed ID ...] [--active ID ...] [--max-brief-chars N]`. The worker cap defaults to 1 and accepts 1–4; the brief limit defaults to 6000 characters and is a character count, not a token estimate. Repeat `--completed` and `--active` once per ID. Input is a UTF-8 JSON object with a nonempty `tasks` array. Each task has a unique trimmed `task_id`, nonempty `goal`, nonempty `writable_paths`, trimmed opaque `worktree_id`, nonempty `acceptance`, optional `depends_on` and `constraints` arrays, and optional `review` (`lead` by default or `independent`). Paths are canonical relative POSIX paths. Extra object fields are ignored.

Validation, including duplicate JSON keys, dependencies, cycles, state IDs, and brief limits, completes before JSON is written. A failure writes a diagnostic to stderr, exits 2, and leaves stdout empty. A task is ready only after every dependency is controller-declared completed. Completed means the controller accepted it; passing tests alone does not establish completion. Selection follows input order and excludes worktree and ancestor/descendant path conflicts, compared case-insensitively. The controller must provide the exact worktree identity: different alias labels do not prove separate worktrees. Unselected tasks appear as deferred (capacity/conflict) or blocked (unmet dependencies); full task specs are not copied into the result.

The brief includes the goal, owned paths, worktree, acceptance, all constraints, review mode, and the decision/escalation invariant. Sol/Astra decides behavior and architecture; Luna/Terra executes. Ambiguous or out-of-scope work stops for escalation. The executor owns tests unless the lead explicitly requests independent review. Independent review is still required wherever project policy requires it.

Default operation is Sol plus one Luna executor. Scale only when tasks are independent and have nonconflicting writable ownership. Each executor owns its tests. The plan is a bounded proposal, not a scheduler; the lead dispatches through Orca and completes its full review, release, and acknowledgement lifecycle.

## Wait

Run `python3 scripts/workflow.py wait --run RUN_ID [--timeout-seconds SECONDS]` in the coordinator terminal bound to the selected Run. The positive finite timeout defaults to 300 seconds. The CLI calls `orca orchestration check` with a bounded wait, and continues internally across empty timeout receipts. At the deadline it emits `event: timeout`, which is a checkpoint rather than a failure. Returned messages include a bounded top-level body preview and metadata, including unknown message types and normalized payload IDs. They are marked for review and remain unacknowledged. Workers read follow-ups only with their exact injected `check --terminal` or `ask` commands; they never bind the coordinator Run or ACK its deliveries. The coordinator owns that ACK. A `consumer_fenced` error is surfaced unchanged and is never auto-rebound or retried. Other runtime, connection, run ID, JSON, or schema errors exit 2 without fallback. This command never acknowledges a delivery.

## Usage

Run `python3 scripts/workflow.py usage PATH` with a UTF-8 JSON object containing a nonempty `sessions` array. Each entry is `{ "path": "relative-or-absolute.jsonl", "session_id": "...", "role": "controller" }` or role `worker`, with optional `start` and `end` supplied together as timezone-aware ISO8601 timestamps. Relative log paths resolve from the manifest directory. The CLI reads only the named JSONL files; it never discovers home directories, accounts, configuration, or environment variables.

The reader streams JSONL and inspects only session metadata, model context, `event_msg` records whose payload type is `token_count`, and `task_started`/`task_complete` events. It never emits prompts, tool output, or other log content. Cumulative counters are validated first; an identical consecutive cumulative checkpoint is counted once and its unused last counters are ignored. Advancing checkpoints must reconcile with last token counters; counter resets and malformed data fail, and the first checkpoint must establish a complete origin. The result reports duplicate checkpoint counts separately from copied manifest sessions. Its model list contains every model observed in the supplied log; token usage is not attributed per model. Caller-supplied roles and expected session IDs are evidence labels, not runtime authorization. Optional cached input and reasoning output remain unknown when unavailable and are treated as subsets, not additional tokens. Zero usage events yield unknown values, not zero.

Identical copied logs with the same session ID and scope are deduplicated only when role, model, and counters agree. Overlapping scopes for one session are rejected. A time window uses event completion timestamps in the half-open interval `[start,end)` and reports adjacent checkpoint boundary timestamps; causal attribution across that window remains unknown. Full-session totals describe only the supplied session and do not prove a dedicated task. Dedicated controller and worker sessions improve attribution; current recovery and preparation work may share session usage unless separated with valid windows. Aggregate metrics include measured-session coverage and remain null when incomplete. Cost is always null; no billing, subscription, or model-price inference is made.

This methodology does not claim an efficiency gain. Any such claim needs a controlled set of real, comparable tasks and accepted outcomes; synthetic examples and functional checks are not benchmark measurements.

The portable synthetic plan in [examples/workflow-plan.json](examples/workflow-plan.json) shows two independent tasks and a dependent integration task. Its worktree IDs are illustrative controller-supplied identities, not machine paths.
